1. Goal

For each piece of work the factory should:

  1. Pick an issue or feature from the issue tracker.
  2. Review and refine the scope (and the design when needed), and get it accepted.
  3. Implement it in the right repositories, open pull requests, and meet the quality bar and CI.
  4. Get it reviewed by agents and humans, and revise until it's approved.
  5. Merge it and verify the deployment.
  6. Watch production, and track, debug and fix critical issues on its own.

This foundation is built so that many agents and people can share one factory safely.

4. Gates

A stage can only be left once its gates pass. Derived gates are computed from the work item. The others are reported by the orchestrator from CI, quality tools and deployment checks. Clients can never set a gate.

MoveGates
Refining → AwaitingApprovalProposalReady (derived)
AwaitingApproval → ReadyScopeApproved (by a human, by default)
Implementing → InReviewPullRequestOpen (derived)
InReview → MergingCiPassing, QualityChecks, ReviewsSatisfied (derived)
Merging → VerifyingMerged
Verifying → DoneDeploymentVerified

When a move is refused, the error lists the gates that are still open, e.g. CiPassing failed (2 tests), ReviewsSatisfied pending. An agent can act on that directly.

5. Many agents, one factory

ClaimsAn expiring lease on the current stage's work, for one role. Agents heartbeat by renewing it. If an agent crashes, its claim expires and another agent takes over.
Humans can always step inAgents need the active claim to act. Humans don't, and only humans can cancel work.
Compare-and-swapEvery change bumps version, and mutations send expected_version. A stale write gets 409 Conflict, so the caller refetches and retries.
Finding workAn idle agent searches claimable_by: implementer and claims the first hit. If it loses the race, it moves on to the next item.
Identity from the tokenThe server derives the acting Actor from the bearer token, so an agent can't act as a human.
Policy per projectWhether a human must approve scope, the review policy (default, issue overrides, floor), and the severity from which incidents are fast-tracked.

6. Reviews

  • Configurable per work item: human only, agent only or human + agent, each with an approval count. The project default is 1 human + 1 agent.
  • Resolved from signals, most specific first:
    1. The project default applies when there are no other signals.
    2. Repository settings (a [review] section in the repo's factory config, or the host's branch restrictions) replace the default. When the work spans several repos, the strictest setting wins.
    3. An issue signal, such as the Jira label review:agent-only, review:human-only:2 or review:human+agent, or a custom field, replaces those if the project allows it.
    4. Enforced repository settings (e.g. a production service always needs a human) and the project floor are minimums. A ticket can't loosen them.
    The work item stores the result together with its signals and a one-line explanation, e.g. repository settings: 2 human approval(s); issue override: 1 agent approval(s); raised to meet minimum 1 human approval(s).
  • Human change requests always block. Agent change requests block only when agent approvals are required; under human only, agent reviews are advisory.
  • No self-review: anyone who implemented the work can't review it or claim its review.
  • Revisions: every re-entry into review starts a new revision. Approvals, CI and quality results from earlier revisions stop counting.
  • A reviewer's latest verdict wins. A Comment never overrides an approval or a change request.

7. Incidents

Alerts from an AlertSource are grouped by fingerprint into Incident work items, one per fingerprint. Critical incidents take the fast track: they skip refinement and approval and go straight to implementation. They still go through review and every gate after that, so a fix never reaches production unreviewed. If a deployment breaks during Verifying, the work goes back to Implementing to be fixed forward.

9. Integration design rules

  1. We own the domain model. Adapters translate vendor payloads, so vendor quirks never reach the UI or the workflow.
  2. Normalised status categories, with the vendor's own name kept for display.
  3. Capability flags instead of a lowest common denominator. The UI shows features only when the provider supports them.
  4. Provider-qualified IDs, e.g. jira:PPL-123 or bitbucket:cover42/tenantservice#456. They're stored as plain strings and checked when parsed.
  5. Escape hatches: extra for vendor-only fields, and IssueQuery::native for raw JQL.
  6. Markdown everywhere. The Jira adapter converts to and from ADF (Atlassian Document Format).
  7. Fakes from day one. In-memory adapters let the server and UI be built without credentials.

11. Server API

REST for actions, and a WebSocket for events. Everything is scoped by project: /v1/projects/{p}/…. A project binds each capability to one provider instance.

POST /v1/projects/{p}/work-items/search          { stages, claimable_by, issue }
POST /v1/projects/{p}/work-items                 { kind, title, issue }
POST /v1/projects/{p}/work-items/{w}/claim       { role, ttl_secs }
POST /v1/projects/{p}/work-items/{w}/advance     { to, note, expected_version }
PUT  /v1/projects/{p}/work-items/{w}/proposal    { proposal, expected_version }
POST /v1/projects/{p}/work-items/{w}/approve-scope
POST /v1/projects/{p}/work-items/{w}/reviews     { verdict, summary }
POST /v1/projects/{p}/issues/search · /pull-requests/search · /pipelines/search
GET  /v1/events?since={seq}                      work_item_updated, agent_run_updated,
                                                 pull_request_updated, alert_updated, …

Errors use one JSON body and map to HTTP statuses: conflict → 409 (refetch and retry), not_allowed → 422 (a workflow rule refused the change), unauthorized → 401 (re-authenticate the provider), unsupported → 501 (hide the feature). Events are numbered, so a client that reconnects catches up on what it missed, or is told to refetch.

13. First adapters

Bitbucket, ported from eisThe eis CLI (Go) already handles OAuth, PRs, default reviewers, pipelines (selector vs pattern) and commit statuses. We port its client logic to Rust instead of calling the CLI. The adapter reads ~/.eiscli/tokens.json first, so an existing eis auth login just works.
Jira, modelled on TWG CLIA Rust client and CLI using TWG's command style: factory jira workitem get|search|query|transition, workitem comment create, space status query. Output is a readable table, or JSON with -o json for agents. It authenticates with an API token first, and OAuth later.

14. Roadmap

  1. ✅ factory-core and factory-api: model, ports, workflow, contract (35 tests).
  2. factory-jira and the factory jira CLI: reads first, then transitions and comments.
  3. factory-bitbucket: PRs, pipelines, commit statuses.
  4. factory-server: SQLite store, REST and events. It runs on the fake adapters first, then the real ones.
  5. Orchestrator: gate reporting from CI and reviews, and syncing new work in from the tracker.
  6. AgentRuntime for Claude Code: planner, implementer and reviewer loops.
  7. Deployment verification, then alert intake and the incident loop.
  8. Desktop "factory floor" view over the event stream.
