1. Context

Software Factory is a desktop app (Rust + GPUI) that brings together the work around shipping software: issues, branches, pull requests, CI, docs and the coding agents that act on them.

At work the stack is Atlassian (Jira, Bitbucket, Confluence). Elsewhere it might be Linear and GitHub. The app should not care which. It speaks to generic capabilities, and each vendor plugs in as an adapter (ports and adapters / hexagonal architecture).

Local git is not a port. Clone, branch, commit and push work the same way against every host, so they live once in core (via the git CLI or gix). Only the hosting APIs need adapters.

4. Design rules

  1. We own the domain model. Adapters translate vendor payloads into our types, so Jira or GitHub quirks never reach the UI.
  2. Normalised status categories. Every workflow status maps to a small fixed set. Jira (status categories) and Linear (state types) both already group statuses this way, so the mapping is reliable. The vendor's own status name is kept for display.
  3. Capability flags, not lowest common denominator. Each adapter reports what it supports (sprints, story points, draft PRs, …). The UI shows features when they're available and hides them otherwise, instead of the core pretending every vendor is identical.
  4. Provider-qualified IDs. For example jira:PPL-123 or bitbucket:cover42/tenantservice#456. They are opaque to the app and can be resolved back to the right adapter.
  5. An escape hatch for vendor-only data. Each entity carries an optional extra: serde_json::Value for things like Jira custom fields, so adapters don't have to drop them.
  6. Async and off the UI thread. All network calls run on GPUI's background executor, and the UI only ever renders cached state.
  7. Fakes from day one. In-memory fake adapters let the UI and workflows be built and tested without network access or credentials.

InReview and Cancelled need a small per-project override map (status name → category), because neither vendor separates them cleanly.

Core entities

EntityKey fields
Issueid, key, title, description (markdown), status {category, name}, assignee, labels, links, url, extra
PullRequestid, repo, source → target branch, title, state (open/draft/merged/declined), author, reviewers + approvals, linked issue ids, url

Personprovider id, display name, email (when available)

Bodies are normalised to Markdown. The Jira adapter converts to and from ADF (Atlassian Document Format).

6. Trait sketches

#[async_trait]
pub trait IssueTracker: Send + Sync {
    fn capabilities(&self) -> IssueCapabilities;
    async fn get_issue(&self, id: &IssueId) -> Result<Issue>;
    async fn search(&self, query: &IssueQuery) -> Result<Page<Issue>>;
    async fn comments(&self, id: &IssueId) -> Result<Vec<Comment>>;
    // writes (milestone 2)
    async fn transition(&self, id: &IssueId, to: StatusCategory) -> Result<()>;
    async fn comment(&self, id: &IssueId, body: &str) -> Result<Comment>;
}

#[async_trait]
pub trait CodeHost: Send + Sync {
    fn capabilities(&self) -> CodeHostCapabilities;
    async fn list_pull_requests(&self, repo: &RepoRef, filter: PrFilter) -> Result<Page<PullRequest>>;
    async fn get_pull_request(&self, id: &PrId) -> Result<PullRequest>;
    async fn review_comments(&self, id: &PrId) -> Result<Vec<ReviewComment>>;
    // writes (milestone 2)
    async fn open_pull_request(&self, req: NewPullRequest) -> Result<PullRequest>;
}

pub struct IssueQuery {
    pub assigned_to_me: bool,
    pub categories: Vec<StatusCategory>,
    pub text: Option<String>,
    pub native: Option<String>, // raw JQL / Linear filter when you need it
}

IssueQuery::native is the query-side escape hatch. The common filters are portable, and power users can still write JQL.

8. Project bindings

A project in Software Factory binds each capability to one configured provider instance. Credentials are stored in the macOS Keychain, never in the config file.

# ~/.config/software-factory/projects/emil.toml
[issues]
provider = "jira"
site     = "https://emil-group.atlassian.net"
projects = ["PPL", "EQ"]

[code]
provider  = "bitbucket"
workspace = "cover42"

[status_overrides]
"Code Review" = "InReview"
"Won't Do"    = "Cancelled"

9. First milestone (proposal)

  1. Convert the repo to a cargo workspace and create factory-core with the model, the traits and fake adapters.
  2. Build the read-only Jira adapter: my issues, an issue's details, comments.
  3. Build the read-only Bitbucket adapter: PRs for a repo, PR detail, build status.
  4. Make a first GPUI screen: "My work". Issues on the left, the linked PRs and their build status on the right.
  5. Then add writes (transition, comment, open PR), and after that the AgentRuntime port.

10. Open questions

Start with Jira and Bitbucket as the first adapters? (Proposed: yes, because they give us real daily data.)
Read-only first, with writes in milestone 2? (Proposed: yes.)
Link issues and PRs by Jira key in the branch name or PR title (e.g. PPL-123), as Atlassian already does? Or keep our own link store as well?
Should the app keep a local cache (SQLite) so it works offline and loads instantly, or always fetch live at first?
Is the factory's core loop "issue → agent works in a worktree → PR → review → merge", with the integrations serving that loop? That would make AgentRuntime the next port after the read-only adapters.
