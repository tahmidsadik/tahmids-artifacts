Task ↔ Email Links

Design proposal · taskservice, notificationservicev2, task frontend, email frontend · 2026-10-15

Recommendation in one line. Link tasks to email threads, store the link in taskservice as a generic task_links row, and let both the email detail view and the task view read from taskservice. Notificationservicev2 only gains two aggregate fields on the thread.

1. Where things stand

Tasks

One single-valued entity link (entityType, entityCode, entityNumber) on the task row, validated at write time by calling the owning service. List is filterable by entity type and code.

Email threads

A thread groups an outbound email with its replies and bounces. It also carries one entity link. The thread detail page in the email frontend is the "email details view".

Between them

Nothing. Taskservice has no gRPC client for notificationservice, and notificationservice has none for taskservice.

2. Decisions

Granularity: thread, not message. A task relates to a conversation, not to one reply. Message-level links multiply rows without adding meaning, and a message always resolves to its thread. A nullable message_code can be added later if a specific message ever needs pinning.
Owner: taskservice. The link is an attribute of the task, exactly like the entity link. One write path, one permission model, and the task list can be filtered by thread code with a plain join. Storing it in notificationservicev2 would force that service to validate task codes and would split "what is this task about" across two databases.
Shape: generic link table, scoped to EmailThread for now. Mirrors the existing EntityRef {type, code}. Documents or comments can be linked later without a new table or new endpoints. The alternative, a dedicated task_email_threads table, costs the same today and one more table next time.

Migration (taskservice)

CREATE TABLE task_links (
  id               serial PRIMARY KEY,
  task_id          integer NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  link_type        varchar NOT NULL,
  link_code        varchar NOT NULL,
  owner            varchar NOT NULL DEFAULT split_part(current_user, ':', 1),
  tenant_hierarchy varchar NOT NULL DEFAULT current_user,
  created_by       varchar NOT NULL DEFAULT 'Emil System',
  created_at       timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT uq_task_links UNIQUE (task_id, link_type, link_code)
);
CREATE INDEX idx_task_links_type_code ON task_links (link_type, link_code);

Taskservice stores only the code. Subject, status and activity of the thread are fetched live, so nothing goes stale.

  rpc AddTaskLink(AddTaskLinkRequest) returns (AddTaskLinkResponse) {}
  rpc RemoveTaskLink(RemoveTaskLinkRequest) returns (RemoveTaskLinkResponse) {}

Protorepo · notificationservice/v1

message EmailThread {
  ...
  uint32 message_count = 10;
  optional google.protobuf.Timestamp last_message_at = 11;
}

Cheap aggregates on the thread query. They let the task view show activity without loading messages and are useful on the thread list as well.

REST · notificationservicev2

No new endpoints. The email frontend calls taskservice directly, as the entity task widget already does for claims and policies. Avoids a notificationservice → taskservice dependency.

Validation and audit

  • Taskservice gets a notificationservice gRPC client config and a resolver for EmailThread, following the existing LinkedEntityResolverService pattern. Unknown thread → 404.
  • Linking requires the task update permission. Viewing linked threads requires the email view permission, which the user already needs to open the thread page.
  • tasks_history is trigger-based on the tasks table and will not see link rows. The changelog producer should emit link and unlink as task updates so the audit trail stays complete.

7. Edge cases

CaseBehaviour
Thread deleted or not visibleTask view shows the code marked unavailable. Link stays until someone removes it.
Task deletedLinks cascade.
Thread reassigned to another entityThe task's own entity link is independent and stays as is. Deliberate: the email link is additional to the entity link.
Same thread linked twiceUnique constraint → 409 or idempotent no-op. Recommend idempotent.
Thread from another tenantTaskservice validates with the caller's headers, so the lookup is tenant-scoped and returns 404.

8. Rollout order

  1. Protorepo: TaskLink, new rpcs, thread aggregate fields. Merge first, PR pipelines compile against master.
  2. Taskservice: migration, entity, notificationservice client + resolver, endpoints, list filter, changelog, e2e specs.
  3. Notificationservicev2: message_count and last_message_at on the thread.
  4. Frontends: tasks panel on the thread page, emails section on the task page.

9. Open question for the team

Generic task_links versus a dedicated task_email_threads table. The recommendation is generic: identical cost now, and it spares a second table and a second set of endpoints the next time something needs to hang off a task.
