Why taskservice, and why a separate table?

OptionWhat it meansVerdict
New table in taskserviceLink is an attribute of the task, like the existing entity link. One write path, one permission model, task list filters by thread with a join.Chosen
Column on tasksemail_thread_code on the task row.No. A column holds one value, so a task could never relate to two emails.
Column on email_threadstask_code on the thread row.No. Same one-value problem, and notificationservice would have to validate task codes.
Table in notificationservicev2email_thread_tasks next to the threads.No. Splits "what is this task about" across two databases, and the task list could not filter by thread without a cross-service call.
Columns in bothEach side stores the other's code.No. Two writes per link, two places to drift, see question 4.
Why link_type + link_code instead of email_thread_code? It mirrors the platform's EntityRef {type, code}. The next thing that hangs off a task, say a document or a comment thread, reuses the same table and endpoints. Cost today is identical.

Question 2Can it handle many-to-many?

Yes. A join table is exactly the many-to-many shape. Each row is one (task, thread) pair. A task appears in as many rows as it has emails, a thread in as many rows as it has tasks. The unique constraint only stops the same pair twice.

Question 3How and when are rows written?

Only by explicit user actions through taskservice, never by background jobs. Nothing is backfilled. Existing tasks and threads start with zero links. Rows appear when someone links, and disappear when someone unlinks or the task is deleted.

    Question 4Do we need to sync between services?

    No. Each fact has exactly one home, and the other side reads it live. Taskservice stores only the thread code. Everything a user sees about the thread (subject, status, last message) is fetched from notificationservicev2 at render time. Nothing is duplicated, so nothing can drift.
    FactStored inRead by
    Which threads a task is linked totaskservice · task_linksBoth views, through taskservice
    Thread subject, status, entitynotificationservicev2 · email_threadsTask view, live via list with code $in
    Message count, last message timeNowhere. Computed from email_messages on readTask view, same call
    Task subject, status, assigneetaskservice · tasksEmail view, live via filters=links.code==
    "Does this thread exist?"Checked once, at link time, via gRPCTaskservice, 404 if not

    Chosen: store the code, read the rest live

    • One write per link, one place to delete.
    • Thread renamed or closed → task view shows it immediately.
    • No Kafka consumer, no reconcile job, no retry logic.
    • Cost: task view makes one extra list call to notificationservice per page load.

    Rejected: copy thread fields into taskservice

    • Subject and status would need a Kafka consumer on thread updates.
    • Core Kafka consumers have no retry or DLQ, so a missed event means a stale row until a sweep fixes it.
    • Closing a thread would require a cross-service write.
    • Saves one read call per page. Not worth a sync pipeline.
