Implementation plan

Task ↔ Email Links · protorepo, taskservice, notificationservicev2, task-sdk, task-management-frontend, nsv2-frontend · 2026-10-16 · Proposed

Summary Tasks get a many-to-many relation to email threads, in addition to the existing single entity link. The relation lives in one new taskservice table, task_links, keyed by (task_id, link_type, link_code) with link_type = 'EmailThread' for now. Taskservice stores only the thread code and validates it against notificationservicev2 at link time. Everything else about a thread is read live, so nothing needs syncing.

Six PRs in four waves. Waves 1 and 2 are backend and can ship without any UI; waves 3 and 4 are SDK and frontend. PR-2 and PR-3 can be reviewed in parallel; PR-5 and PR-6 are independent of each other.

PR-2 · Wave 2taskservice

Branch PPL-XXX/task-email-linksDepends on PR-1 merged; run npm run generate:code after pulling protorepo master

Migration

migrations/<ts>-create-task-links.migration.ts

CREATE TABLE task_links (
  id               serial PRIMARY KEY,
  task_id          integer NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  link_type        varchar NOT NULL,
  link_code        varchar NOT NULL,
  owner            varchar NOT NULL DEFAULT split_part(current_user, ':', 1),
  tenant_hierarchy varchar NOT NULL DEFAULT current_user,
  created_by       varchar NOT NULL DEFAULT 'Emil System',
  created_at       timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT uq_task_links UNIQUE (task_id, link_type, link_code)
);
CREATE INDEX idx_task_links_type_code ON task_links (link_type, link_code);

Plus the RLS policy, copied from the tasks table migration. Additive, no backfill, no downtime. tasks_history is not touched; link changes are recorded through the changelog producer instead.

  5. Staging and production follow the normal promotion. The migration is additive, so no coordination between the services' deploy times is needed.

ScopeOut of scope

  • Backfilling links for existing tasks or threads.
  • Message-level links. A nullable message_code on task_links can be added later without changing the API shape.
  • Automation that creates tasks when an email arrives. The EmailReceived service event already exists for that.
  • Link types other than EmailThread. The table and endpoints accept them structurally, but validation only knows email threads.
