1 · Today

Items vanish

The handler throws, NestJS drops the error, and the inserter is told everything worked. The offset is committed and the item is gone.

2 · Fix only the error

The belt jams

Once the error reaches the consumer, the client seeks back and grabs 42 again at once. No delay, no limit, and nothing behind it moves.

3 · Options

Four blueprints, one blackout

Each lane is one approach. Red hatching is a stopped belt. Purple is an item waiting in a chest while the belt keeps running.

4 · Where retries wait

Belt or robots?

A Kafka retry topic is one more belt, and nothing passes the head item. In SQS every item sits in a chest on its own timer, and a robot fetches it when it is due.

5 · Final design

The retry factory

Three quick tries at the assembler. Then the item goes to the service's retry chest, and robots bring it back every 30 minutes. After the last try, the red chest.

6 · How retries reach the handler

Two inserters, one assembly line

The SQS poller is a second inserter on the same line. Both feed the same four dispatch() steps and the same handler. Only the start and the acknowledgement differ.

7 · Many consumers

Many factories, one mine

Every consumer group gets its own copy of each item. Give each service its own logistic network. With a shared one, other services' robots grab billing's items.

9 · Opting in

One factory at a time

Blueprint · enable consumer retries

  1. Upgrade coreMinor release. Nothing changes yet.
  2. Place the chests<service>-kafka-retry, -kafka-dlq and IAM, in terraform-live
  3. Run the checklistIdempotent handlers, no throw-to-skip, strict ordering marked
  4. Turn it onconsumerRetry.enabled from an env var
  5. Startup checkCore refuses to start if a chest is missing
Stays the same
  • Kafka messages, headers and producers
  • Handler signatures
  • Services that don't opt in
Changes for opted-in services
  • Failures retry, then go to the DLQ
  • An item can run more than once
  • Per-key order is lost after inline retries, unless ordering: 'strict'
  • Malformed items go to the DLQ

11 · Decisions

Researched since the first draft

  • QueuesCreated in Terraform, in terraform-live. Core only looks them up.
  • Attempts4 SQS attempts, 30 minutes apart. After 2 hours the item goes to the red chest (DLQ).
  • Retention14 days in the DLQ is enough. No S3 archive.
  • Not retryableNotFoundException is not retried. Core asks a retry predicate (working name isRetryableException) before every retry. A non-retryable error sends the item straight to the red chest (DLQ), like a malformed item, with no further tries.
  • AlertsEach service owns its DLQ and the alerts on it.
  • Pilotsbilling, changelog and commission services.

Still to decide

  • Retry predicate shape: a core default list plus a per-handler shouldRetry(error) override, or exception classes marked retryable?
