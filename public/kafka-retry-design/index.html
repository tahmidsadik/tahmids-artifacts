Message retry and dead-letter handling

Design proposal for Kafka consumers in @emilgroup/core.

27 Oct 2026 · Tahmid Sadik Draft for review

Diagrams →Nine figures that walk through this proposal, from today's lost-error path to the rollout gates.

Summary

Kafka consumers built on @emilgroup/core never retry and never dead-letter: every handler exception is swallowed inside NestJS, the offset is committed, and the message is lost. The .dlq topics we auto-create are never written to.

This proposal fixes the error path and adds a bounded, non-blocking retry pipeline owned by core: a few fast in-process retries, then delayed retries through per-service retry topics, then a per-service DLQ with full failure context and a redrive tool. Services opt in with one decorator option; rollout is in four phases, with a no-behaviour-change visibility fix first.

Decisions asked of reviewers: per-service (consumer group) DLQ instead of per-topic DLQ; at-least-once with idempotent handlers as the contract; non-blocking retries by default, strict ordering as opt-in.

Current state

A failing @KafkaMessageHandler today is logged once as a generic Internal server error and then committed as if it succeeded. Verified against @emilgroup/core 11.46.0, @nestjs/microservices 11.1.24 and @confluentinc/kafka-javascript 1.8.2.

# Finding Where Effect
F1 Handler errors never reach the consumer. NestJS's RpcProxy catches the exception, the RPC exception filter turns it into a throwError Observable, and Server.handleEvent connects that Observable to a Subject with no subscribers. The error goes nowhere (reproduced with a 5-line rxjs script). kafka-consumer.service.ts calls server.handleEvent(...); @nestjs/microservices/server/server.js handleEvent eachMessage resolves, the offset is stored, the message is lost. Only trace: one RpcExceptionsHandler log line, original error class gone.
F2 With TRACING_ENABLED=true the tracing wrapper catches handler errors and does not rethrow. The workflow variant does rethrow. tracing/trace-injector.ts injectTracingToQueueConsumer (used by both KafkaMessageHandler and the SQS QueueMessageHandler) A second, independent swallow. Also silently breaks SQS redelivery in traced environments.
F3 If F1 and F2 were fixed alone, the confluent client would seek back to the failed offset and re-run the message immediately, forever. The client retry option only covers broker calls, not handler failures. @confluentinc/kafka-javascript _consumer.js #messageProcessor One poison message blocks its whole partition with a hot loop and no backoff.
F4 Unparseable JSON, empty values and a missing event type are logged and dropped with return. kafka-consumer.service.ts eachMessage Malformed messages vanish without a DLQ record.
F5 .dlq topics are auto-created (1 partition, same retention as the source), but nothing in core writes to them. The docs tell services to produce to them by hand. ensureTopics(), docs/auto-create-kafka-topics.md No standard headers, no redrive, and a per-topic DLQ is shared by every consumer group of that topic.
F6 No metrics for handler failures, retries or DLQ volume. Kafka module Loss is invisible until someone notices missing data downstream.

Contrast with SQS. The SQS consumer awaits the handler's Observable with firstValueFrom, so errors propagate and SQS visibility timeout plus redrive policy work as intended (apart from F2). The Kafka transport is the outlier; this design brings it to parity and beyond.

Goals and non-goals

Goals

  • No silent loss: every message either succeeds, is retried, or lands in a DLQ with enough context to act on it.
  • Bounded retries with backoff, configurable per handler, with sane defaults.
  • A poison message must not block its partition for longer than the inline retry budget (seconds, not hours).
  • Retries and redrives affect only the consumer that failed, never other services consuming the same topic.
  • A supported way to inspect, redrive and discard dead-lettered messages.
  • Metrics and alerts for failures, retries and DLQ growth.
  • Opt-in first, so each service can adopt it after checking its handlers are idempotent.

Non-goals

  • Exactly-once processing. The contract stays at-least-once; handlers must be idempotent.
  • Retries for Zeebe/Camunda workers (workflow module already has RetryableWorkerError and a backoff executor).
  • Changing the producer side or topic schemas.
  • Automatic replay of messages already lost before rollout.

Options considered

Option D, a hybrid of short in-process retries and a small set of fixed-delay retry topics, is recommended: it is the only option that both rides out outages lasting minutes and keeps a poison message from blocking its partition.

Option How it works Pros Cons
A. Blocking in-process retry, then DLQ Fix error propagation; retry the handler N times with backoff inside eachMessage; on exhaustion publish to DLQ and commit. Smallest change. Preserves per-partition order. No new topics beyond DLQ. Partition is blocked during backoff. Total budget must stay well under max.poll.interval.ms (300 s default), so it cannot ride out a 10-minute downstream outage.
B. Retry-topic chain only (Spring Kafka / Uber style) Every failure goes straight to a delay-tier topic; each tier consumer waits until due. Non-blocking. Long delays possible. Well-known pattern. Even a 50 ms blip costs a round trip through Kafka and a fixed delay. Breaks per-key ordering on every failure.
C. Database-backed retry Persist failed messages in a service table; a scheduler re-dispatches. Queryable, easy manual edits. Needs a table and scheduler in every service, multi-tenant connection handling, and duplicates what Kafka already offers.
D. Hybrid (recommended) A for 3 fast attempts (about 2 s total); then B with few tiers (default 1 min and 10 min, one topic each); after the last tier, DLQ. Transient blips never leave the partition. Non-blocking after about 2 s. Covers outages of 10+ minutes. 3 extra topics per service. Redrive reuses the retry path. Breaks per-key ordering once a message leaves the inline stage (strict-order handlers opt out, see design). Tier consumers need pause/resume logic.

Each retry topic carries exactly one delay. Because all messages in a tier wait the same time and are appended in failure order, the head of each partition is always the next one due, so a tier consumer can simply pause the partition until the head is due. Mixing delays in one topic would let a 10-minute message block a 1-minute one behind it, which is why tiers are separate topics.

Proposed design

Every failed message moves through three stages owned by core: inline retries, fixed-delay retry tiers, and a per-service DLQ. Handlers stay unchanged apart from one decorator option.

Topology: per consumer group, not per topic

Topic Partitions Retention Purpose
<groupId>.retry.1m 3 7 days First delay tier
<groupId>.retry.10m 3 7 days Second delay tier
<groupId>.dlq 1 30 days Exhausted or non-retryable messages

Tiers are configurable per service; the table shows the default. The existing <topic>.dlq is shared by every consumer group of that topic, so redriving into it, or into the source topic, would re-deliver to every service. Per-group topics carry the source topic in headers and dispatch straight back to the handler that failed. Existing <topic>.dlq topics are left in place and deprecated (see Rollout).

Message lifecycle

Each tier attempt goes back through the same handler and the same inline retries; malformed messages skip straight to the DLQ.

  1. Dispatch and await. KafkaConsumerServer overrides handleEvent to await the handler's Observable (lastValueFrom), as the SQS transport already does. A Kafka-only exception filter rethrows the original error so its class survives. This fixes F1. The tracing wrapper rethrows after recording the span (F2).
  2. Success → offset is stored, as today.
  3. Failure → classify the error (below). Non-retryable goes straight to the DLQ.
  4. Inline retries. Up to 3 attempts with exponential backoff and jitter (200 ms, 600 ms, 1.8 s; about 2.6 s worst case). The partition waits only this long.
  5. Escalate to a tier. Publish a copy to the next tier topic with retry headers, await the broker ack, then let the offset commit. If the publish fails, the error is thrown so the client seeks back and the message is retried later: never lost, possibly duplicated.
  6. Tier consumer. One extra consumer per service (group <groupId>.retry) reads all its tier topics. If a partition's head is not yet due (x-retry-not-before), it pauses that partition and resumes at the due time. When due, it dispatches to the handler named by x-original-topic + x-event-type, with the same inline retries.
  7. Exhausted after the last tier → DLQ, offset commits, an alert fires.
  8. Malformed input (bad JSON, empty value, no event type; F4) → DLQ with x-error-class: MalformedMessage instead of being dropped.

Error classification

  • New export NonRetryableKafkaError: throw it (or wrap a cause in it) to skip retries.
  • Non-retryable by default: MalformedMessage, BadRequestException, UnprocessableEntityException, class-validator validation errors.
  • Retryable by default: everything else, including timeouts, gRPC UNAVAILABLE, DB connection errors and NotFoundException (often eventual consistency; see open questions).
  • Per-handler override: retry.isRetryable(error) => boolean.

Headers added on retry and DLQ

All original headers are kept (x-tenant-slug, x-correlation-id, x-user-id, x-event-type, …). Core adds:

Header Example Notes
x-original-topic / -partition / -offset eis.account.events / 2 / 18734 Together form the stable message id used for dedup
x-original-timestamp 1761552000000 First produce time
x-consumer-group accountservice Group that failed
x-retry-attempt 4 Total attempts so far, inline included
x-retry-tier retry.1m Tier the message is in
x-retry-not-before 1761552060000 Epoch ms; tier consumer waits until then
x-error-class QueryFailedError Last error's constructor name
x-error-message connect ECONNREFUSED … Truncated to 1 KB, no stack
x-failed-at 1761552001200 Time of the last failure
x-redriven-at / x-redriven-by … / <user sub> Set only by the redrive tool

Ordering

Default mode is non-blocking: once a message leaves the inline stage, newer messages with the same key can be processed before it. Handlers that need per-key order (for example balance updates) set ordering: 'strict': inline retries continue in place with backoff capped at 30 s for up to 4 minutes (inside max.poll.interval.ms), then the message goes to the DLQ and the partition continues, or, with onExhausted: 'pause', the partition stays paused until someone redrives or discards it.

Idempotency contract

Retries and redrives make duplicates normal. Core exposes the stable id <original-topic>:<partition>:<offset> via a new @KafkaMessageMeta() parameter decorator so handlers can dedupe. IdempotencyManager gets a runWithMessageIdempotency(meta, work) method mirroring the existing runWithJobIdempotency for Zeebe jobs. Adopting retry on a handler requires confirming it is idempotent; this is the main per-service checklist item.

Redrive tooling

  • KafkaDlqService (core): list(filter), redrive(filter), discard(filter). Filters: event type, tenant, error class, time range, offsets.
  • Redrive publishes to the first tier with x-retry-attempt reset and x-redriven-* set; it never writes to the source topic, so only the failing service sees the message again. Discarding commits past the message in a dedicated <groupId>.dlq-admin group, keeping an audit log line.
  • Exposed as an internal, platform-admin-only REST endpoint registered by KafkaModule and as an eis kafka dlq CLI command that calls it.

API and per-service configuration

A service turns the pipeline on once in KafkaModule config and tunes it per handler; all new fields are optional, so this ships as a minor release.

Module level (new consumerRetry block in ConfigParams):

KafkaModule.register({
  kafka: kafkaOptions,
  topicConfigs,
  consumerRetry: {
    enabled: true,                    // default false until Phase 4
    inline: { attempts: 3, initialDelayMs: 200, multiplier: 3, jitter: true },
    tiers: ['1m', '10m'],             // one topic per entry: <groupId>.retry.1m, .retry.10m
    dlq: { retentionMs: RetentionMs.ThirtyDays },
    redriveEndpoint: true,            // registers the platform-admin DLQ endpoint
  },
});

Handler level (optional third argument to the existing decorator):

@KafkaMessageHandler(ACCOUNT_DOMAIN_TOPIC, 'account.created', {
  retry: { tiers: ['1m', '10m', '10m'], isRetryable: (e) => !(e instanceof DuplicateAccountError) },
})
async onAccountCreated(@Payload() data: AccountCreated, @KafkaMessageMeta() meta: KafkaMessageMeta) {
  await this.idempotency.runWithMessageIdempotency(meta, () => this.syncAccount(data)); // new, mirrors runWithJobIdempotency
}

@KafkaMessageHandler(BILLING_DOMAIN_TOPIC, 'invoice.paid', { ordering: 'strict', onExhausted: 'pause' })
async onInvoicePaid(@Payload() data: InvoicePaid) { /* ... */ }

@KafkaMessageHandler(AUDIT_DOMAIN_TOPIC, 'audit.logged', { retry: false }) // DLQ on first failure

A handler's tiers may repeat or skip entries of the module's tier list but cannot add new delays, since each delay is a topic.

New exports (all additive): NonRetryableKafkaError, KafkaMessageMeta (decorator + type with messageId, attempt, originalTopic, isRedrive), KafkaDlqService, KafkaRetryHeaderKeys, KafkaHandlerOptions.

Topic creation. ensureTopics() creates the tier and DLQ topics for the consumer group when consumerRetry.enabled is true, independent of topicConfigs (which only lists topics the service produces). In environments where services lack create-topic ACLs, the topics are added to the platform topic list instead (open question).

Observability and operations

A message reaching a DLQ pages nobody but always raises a ticket-level alert; a growing retry backlog is the early warning.

Metrics (OpenTelemetry, labels consumer_group, topic, event_type, error_class):

Metric Type Alert
kafka_consumer_handler_failures_total counter none; dashboards only
kafka_consumer_retries_total (+ stage = inline / tier) counter none
kafka_consumer_dlq_total counter any increase in 5 min → warning to the owning team's channel
kafka_consumer_retry_backlog gauge, messages not yet due per tier above a per-service threshold for 15 min → warning
kafka_consumer_dlq_publish_failures_total counter any increase → critical (messages are looping)

Logs. One structured error line per failure with correlationId, tenantSlug, message id, attempt, tier and error class. Inline attempts before the last log at warn.

Tracing. Each attempt is a span on the original trace with messaging.retry.attempt; the tracing wrapper records the exception and rethrows.

Runbook (per DLQ alert)

  1. eis kafka dlq list <service> --since 1h to group entries by event type and error class.
  2. Fix the cause (deploy, data fix, downstream recovery).
  3. eis kafka dlq redrive <service> --event <type> --since <time>; watch kafka_consumer_dlq_total stay flat.
  4. Messages that should never be processed: eis kafka dlq discard … with a reason, which is logged for audit.

Data protection. DLQ messages keep the original payload and headers, including x-api-key and personal data. DLQ topics get the same ACLs as the source topics, the CLI masks x-api-key, and retention is capped at 30 days.

Rollout and migration

Rollout runs in four phases; only Phase 4 changes default behaviour, and it is a major release. Phase 1 ships the propagation fix and bounded retries together on purpose: fixing error propagation (F1) without bounded retries turns every poison message into an infinite hot loop (F3).

Phase Ships core version Behaviour change Exit gate
0. Visibility Log the real error class and message for swallowed Kafka handler errors; add kafka_consumer_handler_failures_total. patch None One week of failure counts per service, so we know how much is being lost today.
1. Retry + DLQ, opt-in F1 fix behind consumerRetry.enabled; inline retries; per-group DLQ; F4 malformed messages to DLQ; F2 rethrow scoped to Kafka; KafkaMessageMeta; DLQ metrics. minor Only for services that opt in One pilot service runs 2 weeks in TEST and 1 week in production with zero lost messages and no partition stalls.
2. Delay tiers + redrive Tier topics and tier consumer; KafkaDlqService; admin endpoint; eis kafka dlq CLI; alerts. minor Only for opted-in services Pilot redrives a real DLQ batch end to end; runbook reviewed by on-call.
3. Adoption Each team confirms handler idempotency, enables consumerRetry, sets strict ordering where needed. service PRs Per service All Kafka-consuming services enabled.
4. Default on consumerRetry.enabled defaults to true; F2 rethrow for SQS too; createDlqTopics and <topic>.dlq constants deprecated. major Everyone n/a

SQS side effect of F2. Making the SQS tracing wrapper rethrow means failed SQS messages start returning to their queues in traced environments, which is correct but may surface redelivery volume that was hidden. That is why it waits for Phase 4 and needs confirmation that every SQS queue has a redrive policy.

Existing <topic>.dlq topics. Nothing writes to them through core. Before deprecating, search services for manual producers to *_DOMAIN_TOPIC_DLQ; any found move to KafkaDlqService.

Risks and open questions

Risks

Risk Mitigation
Non-idempotent handlers double-apply effects on retry or redrive. Opt-in per service with an idempotency checklist; KafkaMessageMeta.messageId + runWithMessageIdempotency.
Retries amplify load on a struggling downstream. Inline budget is about 2.6 s; tiers are fixed delays, not tight loops; retry_backlog alert.
Non-blocking retries reorder events for the same key. ordering: 'strict' for handlers that need order; teams list such handlers during adoption.
Overriding handleEvent couples us to NestJS Server internals. Covered by an e2e spec in src/tests/kafka that asserts a throwing handler reaches the consumer; re-run on every NestJS bump.
Tier consumer pause/resume misbehaves across rebalances. Re-evaluate due times on every assignment; integration test with a forced rebalance.
3 extra topics per service increase cluster partition count. 7 partitions per service at defaults; check against MSK limits before Phase 4.
