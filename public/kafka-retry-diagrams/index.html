Kafka retry and dead-letter design, in diagrams

A visual companion to the design proposal. Each figure makes one point; the proposal has the full reasoning, API and open questions.

Code references are against @emilgroup/core 11.46.0, @nestjs/microservices 11.1.24 and @confluentinc/kafka-javascript 1.8.2.

What you are deciding

  1. Hybrid retry: three inline attempts, then 1-minute and 10-minute retry topics, then DLQ (fig 03, 04).
  2. Retry and DLQ topics per consumer group instead of the current per-topic .dlq (fig 05).
  3. At-least-once delivery with idempotent handlers as the contract; strict ordering only where a handler opts in.

The problem

Fig 01 · today

A handler error never reaches Kafka, so the offset is committed and the message is lost

Check: the fix overrides handleEvent in KafkaConsumerServer to await the Observable, the way the SQS transport already does with firstValueFrom.

Fig 02 · one partition, offsets 40 to 47

Fixing propagation alone would trade silent loss for a partition stuck on one bad message

Options

Fig 03 · options A to D

Only the hybrid keeps the partition free after a few seconds and still rides out a 10-minute outage

The design

Fig 04 · message lifecycle

Every failure ends in a commit or the service's DLQ, never in silence

Check: publishing to the next tier is awaited before the offset commits. If the publish fails, the error is thrown and the client re-reads the message: a duplicate is possible, a loss is not.

Fig 05 · topic layout, example topic eis.account.events

Retry and DLQ topics belong to the consumer group, so a redrive only reaches the service that failed

Decide: deprecate the existing per-topic .dlq topics and their generated *_DOMAIN_TOPIC_DLQ constants in Phase 4.

Fig 06 · why each delay gets its own topic · now 10:00

Mixing delays in one topic lets a 10-minute message hold back 1-minute ones

Fig 07 · example record in billing.dlq

A DLQ record keeps the original message and adds what an engineer needs to act on it

Operating it

Fig 08 · redrive after an incident

Redrive goes through the group's first retry tier, never the source topic

Open: which team owns DLQ alerts, the consuming service's team or platform on-call.
