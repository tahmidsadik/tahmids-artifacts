Which product documents does a customer actually receive?

When a workflow sends product documents with a lead or policy email, documentservice ignores the product version. Two more problems decide what lands in the inbox: only the first page of documents is fetched, and on staging notification-core overwrites attachments that share a file name.

Data: read-only queries on test and staging, 16 Oct 2026Code: documentservicev2 master, @emilgroup/core 11.40.0, notification-core 27624f7

The short answer

The customer should get the documents of the product version their policy or lead is on. Today they get documents from every version of the product, oldest first, cut off after one page.

On staging that has two outcomes for the big Allianz products. With the default page size of 10, customers get only the old version and the latest version is never fetched. With a page size big enough to hold everything, the overwrite bug makes the latest version win every name conflict, but the email still carries one copy per version.

How a document gets to the inbox

Three problems along one path

BPMN · document:product_document_list

1. Workflow asks for documents

The worker reads the product slug from the job (productSlug, payload.productSlug or payload.policy.product.slug) plus optional filters and pageSize.

The policy's or lead's product version is never read.
ProductDocumentEntityQuery

2. Query by slug only

product_slug = X, plus type or slug filters. productVersionId isn't a filterable column, so the BPMN can't add it either.

Returns every version's documents.
paginateList → nestjs-paginate

3. Oldest first, one page

No sort is passed, so nestjs-paginate falls back to sortableColumns[0], which is id ASC. Page size defaults to 10, at most 50. Only page 1 is used.

Newest documents fall off the end.
notification-core · downloadAttachmentsToTmp

4. Download and attach

Every attachment goes to /tmp/<uuid>/<name>. Attachments with the same name share one path, so each download overwrites the previous one.

Staging only. Fixed in 27624f7 (PPL-1142).
The staging overwrite

Last download wins, but every attachment is still sent

The loop runs in list order. Each entry in FileAttachments keeps its own index but points at the shared path. The email is built after all downloads finish, so every same-named attachment reads the file that was written last.

Before the fix

# attachments in list order (id ASC)
[0] v6996  → /tmp/a1/allianz_phv_ipid.pdf
[1] v7001  → /tmp/a1/allianz_phv_ipid.pdf  overwrites [0]

# built email
allianz_phv_ipid.pdf  content: v7001
allianz_phv_ipid.pdf  content: v7001

Two attachments with the same name and identical content. The v6996 file is gone.

After 27624f7

# one directory per attachment index
[0] v6996  → /tmp/a1/0/allianz_phv_ipid.pdf
[1] v7001  → /tmp/a1/1/allianz_phv_ipid.pdf

# built email
allianz_phv_ipid.pdf  content: v6996
allianz_phv_ipid.pdf  content: v7001

No data loss, but the customer now clearly gets both versions. The fix makes the documentservice problem easier to see. It doesn't solve it.

Data findings

What the databases show

  • Where a name conflicts, the latest version always has the higher id. That held for all 33 conflicting groups on test and all 23 on staging, because tenants created documents one version after another. So with the overwrite bug, the latest version wins whenever it's fetched at all.
  • The page size decides more than the overwrite bug does. In bas-stage/allianz_phv, allianz_wgv, emil-demo/allianz_phv and garantiemax-test/kitchen-comfort, the old version fills ids 1–10. With page size 10 there's no conflict at all; customers just get the outdated set.
  • bas-stage/allianz_vh version 6997 holds liability (PHV) documents. All eleven of its rows use allianz_phv_* slugs. With page size 10, a household (Hausrat) customer is sent liability terms and none of the household terms on version 7000. This looks like a data error to fix separately.
  • Filenames repeat within one version. In allianz_phv, the couples, family and single documents share one filename. If notification-core names attachments after the filename column, they overwrite each other even inside a single version.
  • Id order doesn't always match version order. In enzo-test/hausratversicherung, version 724's document is older than version 628's. No conflict there today, but "highest id wins" is not a safe stand-in for "latest version".
Proposals

How to fix it

Proposals 1 and 2 fix the behaviour. 3 and 4 limit the damage until then and clean up what the investigation found.

1
Must · documentservice

Send the documents of the entity's product version

  • Add productVersionId to filterableColumns in product-document.config.ts and a filterByProductVersionId to ProductDocumentEntityQuery.
  • In the ListProductDocument worker, read the version from the job, for example productVersionId, then payload.policy.productVersionId, then the lead's version, and always filter on it.
  • If no version can be found, fail the task with a clear error. Never fall back silently to all versions.
  • Roll out per tenant at first, using a custom header such as matchProductVersion: true, so existing BPMNs that work around today's behaviour don't change overnight. Make it the default once tenants are checked.
2
Must · documentservice

Fetch every page, in an explicit order

  • Follow nextPageToken in the worker until it's empty, so a product with more than 10 or 50 documents isn't cut short.
  • Pass an explicit order instead of relying on nestjs-paginate's fallback, so the attachment order is a decision and not an accident.
3
Should · notification-core

Ship the overwrite fix and make names unique

  • Deploy 27624f7 (PPL-1142) to staging. It stops data loss but, until 1 and 2 land, customers will visibly get both versions.
  • When two attachments in one email share a name, add a suffix (AVB (2).pdf) so the customer can tell them apart.
4
Could · data and config

Clean up data and check the workflows

  • Fix bas-stage/allianz_vh version 6997, which holds PHV documents.
  • List every BPMN that uses document:product_document_list and record its pageSize, filters and attachment mapping. That tells us which simulator setting each tenant is on today.
  • Add a test that lists documents for a product with two versions and asserts only the policy's version comes back.

Needs a product decision

  • Missing document on the policy's version. If version 3 has no terms because the tenant only re-uploaded changed files, should we send the newest earlier version's terms? Exact match is simplest. "Newest per slug at or below the policy's version" fits tenants who upload only changes.
  • Leads. Check in insuranceservice that lead payloads carry a product version the way policies do.
