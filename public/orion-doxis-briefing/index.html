Short version

Five things to know before the call

  • Alabus never talks to Doxis directly. Inacta's middleware, the IIL, does the work: it polls an Alabus database copy, builds the dossiers, classifies documents and writes everything into Doxis.
  • When EIS replaces Alabus, EIS must supply everything the IIL reads from that copy today: master data, business keys, document IDs, case closure and deletion triggers.
  • The open decision that matters most is who builds dossiers and classifies documents in the target: EIS calling Doxis directly, or the IIL reading from EIS.
  • About 90% of retention rules live in Alabus today. They have to be reverse-engineered and moved to EIS.
  • We can log in to the Doxis portal but have no REST API access yet. That's the first thing the call has to fix.

AS-IS

How the pieces behave

Doxis data model

  • One dossier each per partner, policy, legal case and offer. The partner number is the master reference that links them.
  • A policy dossier has subfolders for its documents, related claims, finance and complaints.
  • Each document has about 20 metadata fields. About 18 are value lists (GVL_*) that hold Alabus codes today.
  • Document class: department + document type → DocType / subcategory via Orion's NOVA-500 table, then rules R1–R9 pick the class (legal case, contact, offer, policy, finance or residual).
  • Doxis numbers nothing itself. Every key comes from the core system.

Rules that live in Alabus

  • About 90% of retention rules, on several levels: offers 30 days unless signed, Verlustscheine 20 years, finance 10 years, others X years after last client contact.
  • A daily anonymisation list of contact, insured and partner numbers. Doxis deletes the documents linked to them.
  • Closing a legal case freezes its documents in Doxis. Reopening happens in the core system.
  • Doxis holds one rule itself: documents without a contact number (old migrated data) go after 10 years.

How case handlers work

  • Mostly in Doxis: correspondence, documents, emails written from Doxis templates.
  • Activities, coverage and closing a case happen in ORIS. Both stay open side by side; the RF number is copied between them.
  • Filters used most: document type and subtype. Old versions stay visible.
  • Access is per department. Employee cases are the one exception.
  • Many reply straight from Outlook because filing through Inadox takes too long.

Decision

Three ways to connect EIS and Doxis

Logged as Q-A7 / Q-T4. It sets the size of the epic and how generic the connector can be.

OptionHow it worksForAgainst
A · EIS → DoxisEIS calls the Doxis REST API for documents and dossiers, and does classification, enrichment and dossier sync itself.No Inacta dependency at runtime. Matches “no intermediate layer”.EIS rebuilds Orion-only logic (NOVA-500, R1–R9, E1–E4, 5 dossier types). Not generic.
B · EIS → IILEIS sends documents and keys to the IIL. The IIL reads master data from EIS instead of the replica.Orion logic stays where it is. EIS only exposes generic APIs.Runtime dependency on Inacta. Two parties must agree an interface.
C · Mixed RecommendedEIS pushes documents straight to Doxis. The IIL keeps dossier sync and the Inadox feed, fed by EIS events.Splits work along today's boundaries. Keeps Orion logic out of the product.Two paths to keep consistent.

Recommendation: option C, driven by events

  • Build a generic DMS layer in EIS with one adapter per DMS. It covers document push, search, lifecycle (close / freeze) and delete. Wertgarantie's DMS becomes another adapter.
  • The Doxis adapter calls the REST API directly. Orion's document-type mapping and value lists are tenant configuration, not code.
  • EIS publishes master-data change events that the IIL reads instead of polling the Alabus replica. This also beats today's 5-minute latency.
  • Retention rules move into EIS because EIS owns the master data. Doxis can still execute the deletion.
  • Absorb pieces of the IIL later if that pays off. It isn't on the critical path for go-live.

Contradictions to settle

  • Deletion. The attribute inventory says nothing is ever deleted in Doxis. The 5 Nov sync says Doxis deletes documents from Alabus's daily anonymisation list.
  • Claim documents. The BRD says they are created only in Doxis. Alabus archives claim-department documents today (cost approvals, powers of attorney, invoices).
  • Who creates dossiers. We assumed a dossier appears with the first document. Today the IIL creates every dossier from master data.

Questions for Matthias

  1. What is the REST base URL for Orion-Dev?
    /restws on the webcube host returns 404.
  2. How do we get a technical user, and which login does it use?
    The API supports API key, JWT, OIDC, SAML and mTLS. Our accounts are supervisors on a shared 10-seat licence.
  3. Which repository IDs and document type IDs does Orion use? Can we read the schema service?
    GET /documentTypes and /attributeDefinitions give us the mandatory fields and lengths per type.
  4. Can Doxis notify EIS through webhooks or external events?
    Needed for documents from Outlook, scans and FNOL to show up without polling.
  5. Can the IIL consume EIS (events or API) instead of the Alabus replica?
    This settles who builds dossiers (Q-A7).
  6. Can Orion share the NOVA-500 type mapping and the value-list contents?
    Without them we can't classify EIS documents or map status codes.
  7. Should live document searches run as the user (SSO) or as a service user?
    A service user could expose employee-case documents in EIS.
