Kafka consumer retries

Today a Kafka handler that throws loses its message. This draft retries it in place first, then parks it in the service's own SQS queues until it succeeds or someone acts on it.

The problem

A failing handler loses its message

NestJS turns the handler's error into an Observable that nothing subscribes to, so the consumer thinks the message succeeded.

Fixing only the swallowed error creates a hot loop

If the error reaches the consumer, the Kafka client seeks back and re-reads the same message immediately, with no backoff and no limit.

Options

Where a failing message waits

Each lane is one approach. Red blocks the partition; teal waits somewhere else while the partition keeps moving.

Where retries wait

Kafka retry topics or SQS?

A Kafka partition is read in order, so a delayed message at the head holds up everything behind it. An SQS message has its own timer.

SQS gives us

  • A wait per message, up to 12 h
  • Built-in DLQ and redrive
  • Queue-depth alarms in CloudWatch
  • No extra Kafka topics or partitions

SQS costs us

  • 14-day maximum retention
  • 1 MiB messages, 10 attributes
  • Reading a message hides it for a while
  • Queues and IAM set up per service

Final design

Retry in place, then wait in SQS

Pick a case or let them cycle. Times are compressed.

Two pollers, one dispatch path

Core runs an SQS poller next to the Kafka consumer. Both call the same dispatch(), so handlers can't tell where a message came from.

Topics with many consumers

Queues belong to a service, not a topic

Every service reads its own copy of a message. A retry must reach only the service that failed.

Rules that follow

  • Retries and redrives never write back to the Kafka topic
  • Each service's groupId must be unique
  • Count attempts in the message, not with SQS's receive count

Also fixed in core

  • Two handlers for the same topic + event: fail at startup (today the second one silently replaces the first)
  • Shared idempotency store: key includes the consumer group

The SQS message

Kafka messages stay as they are

Core wraps the original message in a body only core reads. SQS allows 10 attributes, so everything goes in the body.

Opting in

One service at a time

  1. Upgrade coreMinor release. Nothing changes yet.
  2. Create queues<service>-kafka-retry, -kafka-dlq and IAM, in terraform-live
  3. Run the checklistIdempotent handlers, no throw-to-skip, strict ordering marked
  4. Turn it onconsumerRetry.enabled from an env var
  5. Startup checkCore refuses to start if a queue is missing

Stays the same

  • Kafka messages, headers and producers
  • Handler signatures
  • Services that don't opt in

Changes for opted-in services

  • Failures retry, then go to the DLQ
  • A message can run more than once
  • Per-key order is lost after inline retries, unless ordering: 'strict'
  • Malformed messages go to the DLQ

Decisions

Decided since the first draft

QueuesCreated in Terraform, in terraform-live. Core only looks them up.
Wait30 minutes between SQS attempts.
Retention14 days in the DLQ is enough. No S3 archive.
Not retryableNotFoundException is not retried. Core asks a retry predicate (working name isRetryableException) before every retry.
AlertsEach service owns its DLQ and the alerts on it.
Pilotsbilling, changelog and commission services.

Still to decide

  • How many 30-minute SQS attempts before the DLQ? The animation assumes 4, so 2 hours.
  • Where a non-retryable error goes: straight to the DLQ (like a malformed message), or logged and committed?
  • Retry predicate shape: a core default list plus a per-handler shouldRetry(error) override, or exception classes marked retryable?
